Project Guide: Cross-Chain Token Bridge with VIA Labs
This document provides a complete guide for developing, deploying, and interacting with a cross-chain token bridge. The architecture is inspired by Hyperlane's modular design and powered by the VIA Labs messaging protocol.

1. Project Overview 🗺️
The goal of this project is to enable assets to move between blockchains. We will implement two distinct patterns using a shared, modular router architecture:

Burn-and-Mint (ViaERC20.sol): For creating a new, native omnichain token whose total supply is constant across all chains. When tokens move from Chain A to Chain B, they are burned on A and minted on B.

Lock-and-Unlock (ViaERC20Collateral.sol): For "wrapping" an existing, single-chain token (e.g., wPLS on PulseChain). Tokens are locked in a collateral contract on Chain A, and a representative "wrapped" token is minted or unlocked on Chain B.

Both patterns will use a central ViaTokenRouter.sol contract to handle the messaging logic, keeping the code clean and reusable.

5. Smart Contract Development Guide ✍️
Here is the full code and explanation for each contract.

contracts/routers/ViaTokenRouter.sol
This is the abstract, reusable core of our architecture. It inherits from VIA's MessageClient and handles the generic logic for sending and receiving messages, delegating the specific actions (mint/unlock) to the child contracts.

Solidity

// SPDX-License-Identifier: MIT
pragma solidity =0.8.17;

import "@vialabs-io/npm-contracts/MessageClient.sol";

abstract contract ViaTokenRouter is MessageClient {
    /**
     * @notice Handles incoming messages from VIA's protocol. It decodes
     * the basic transfer data and passes it to the child contract.
     */
    function _processMessage(uint, uint, bytes calldata _data) internal virtual override {
        (address recipient, uint256 amount) = abi.decode(_data, (address, uint256));
        _handleTransfer(recipient, amount);
    }

    /**
     * @notice Dispatches a message to the destination chain using VIA.
     */
    function _dispatchMessage(
        uint32 _destChainId,
        address _recipient,
        uint256 _amount
    ) internal virtual {
        _sendMessage(_destChainId, abi.encode(_recipient, _amount));
    }

    /**
    * @notice Abstract function to be implemented by child contracts
    * with specific token logic (e.g., minting or unlocking).
    */
    function _handleTransfer(address _recipient, uint256 _amount) internal virtual;
}
contracts/patterns/ViaERC20.sol
This is the Burn-and-Mint implementation for your native omnichain token.

Solidity

// SPDX-License-Identifier: MIT
pragma solidity =0.8.17;

import "../routers/ViaTokenRouter.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20BurnableUpgradeable.sol";

contract ViaERC20 is ERC20Upgradeable, ERC20BurnableUpgradeable, ViaTokenRouter {
    
    function initialize(
        string memory _name,
        string memory _symbol,
        uint256 _initialSupply
    ) public initializer {
        __ERC20_init(_name, _symbol);
        __ERC20Burnable_init();
        MESSAGE_OWNER = msg.sender; // Set owner for VIA's MessageClient
        if (_initialSupply > 0) {
            _mint(msg.sender, _initialSupply); // Only on the "home" chain
        }
    }

    function bridge(uint32 _destChainId, address _recipient, uint256 _amount) external {
        _burn(msg.sender, _amount); // Burn tokens on source chain
        _dispatchMessage(_destChainId, _recipient, _amount);
    }

    function _handleTransfer(address _recipient, uint256 _amount) internal override {
        _mint(_recipient, _amount); // Mint tokens on destination chain
    }
}
contracts/patterns/ViaERC20Collateral.sol
This is the Lock-and-Unlock implementation for wrapping an existing token.

Solidity

// SPDX-License-Identifier: MIT
pragma solidity =0.8.17;

import "../routers/ViaTokenRouter.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract ViaERC20Collateral is ViaTokenRouter {
    using SafeERC20 for IERC20;
    
    IERC20 public immutable wrappedToken;

    constructor(address _wrappedToken) {
        wrappedToken = IERC20(_wrappedToken);
        MESSAGE_OWNER = msg.sender; // Set owner for VIA's MessageClient
    }

    function bridge(uint32 _destChainId, address _recipient, uint256 _amount) external {
        // Lock tokens in this contract
        wrappedToken.safeTransferFrom(msg.sender, address(this), _amount);
        _dispatchMessage(_destChainId, _recipient, _amount);
    }

    function _handleTransfer(address _recipient, uint256 _amount) internal override {
        // Unlock tokens and send to recipient
        wrappedToken.safeTransfer(_recipient, _amount);
    }
    
    function totalLocked() external view returns (uint256) {
        return wrappedToken.balanceOf(address(this));
    }
}

Post-Deployment Configuration (CRITICAL):
After deploying, your contracts need to know about each other. You must call a function on each MessageClient contract to set its "trusted remote" address for each chain path. This ensures messages are only accepted from your own contracts on other chains.

This is typically done by calling a function like setRemote(uint32 _chainId, bytes32 _remoteAddress) on the MessageClient contract. Consult the VIA Labs documentation for the exact function name and format.

7. Usage Guide 🔀
After deployment and configuration, users can interact with the bridge() function on your contracts to move assets. You can create a Hardhat task or a simple script to do this.

Example Interaction Script (scripts/bridge.js):

JavaScript

const hre = require("hardhat");

async function main() {
    const [signer] = await hre.ethers.getSigners();
    const contractAddress = "your_deployed_contract_address";
    const tokenAddress = "address_of_token_to_bridge";
    const amount = hre.ethers.utils.parseEther("100"); // Bridge 100 tokens
    
    const Bridge = await hre.ethers.getContractAt("ViaERC20Collateral", contractAddress);
    const Token = await hre.ethers.getContractAt("IERC20", tokenAddress);

    // 1. Approve the bridge to spend tokens
    console.log("Approving token spend...");
    await Token.connect(signer).approve(Bridge.address, amount);
    
    // 2. Call the bridge function
    console.log("Bridging tokens...");
    const destinationChainId = 11155111; // Example: Sepolia Testnet Chain ID
    const recipientAddress = signer.address;

    const tx = await Bridge.connect(signer).bridge(destinationChainId, recipientAddress, amount);
    await tx.wait();

    console.log("Bridge transaction sent! Hash:", tx.hash);
}

main().catch((error) => {
    console.error(error);
    process.exitCode = 1;
});

Guiding Principles for Integration 🎯
The best place to manage fees is in the reusable ViaTokenRouter.sol contract. By adding the fee logic here, both the ViaERC20 (burn-and-mint) and ViaERC20Collateral (lock-and-unlock) contracts will automatically inherit the functionality without duplicating code.

We will implement the Dynamic Fee Collection model, where fees for the source chain (FEE_TOKEN) and destination gas (WRAPPED_GAS_TOKEN) are collected from the user with every bridge transaction.

Step 1: Upgrading ViaTokenRouter.sol with Fee Management
Here is the updated ViaTokenRouter contract. It now includes state variables for fees, access-controlled functions to manage them, and emergency recovery mechanisms.

Solidity

// SPDX-License-Identifier: MIT
pragma solidity =0.8.17;

import "@vialabs-io/npm-contracts/MessageClient.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/access/Ownable.sol"; // Using Ownable for clear access control

abstract contract ViaTokenRouter is MessageClient, Ownable {
    using SafeERC20 for IERC20;

    // --- State Variables for Fees ---
    IERC20 public feeToken; // Token for source fees (e.g., USDC)
    IERC20 public wrappedGasToken; // Token for destination gas (e.g., WETH)

    mapping(uint32 => uint256) public sourceFees;
    mapping(uint32 => uint256) public destinationGasFees;

    // --- Fee Protection ---
    mapping(uint32 => uint256) public maxFeeLimits;
    mapping(uint32 => uint256) public maxGasLimits;

    // --- Modifier for Owner-Only Functions ---
    // Note: We are using OpenZeppelin's Ownable for clarity over MessageClient's MESSAGE_OWNER
    // Ensure the owner is set correctly in the child contract's initializer.

    // --- Core Messaging Logic (from before) ---
    function _processMessage(uint, uint, bytes calldata _data) internal virtual override {
        (address recipient, uint256 amount) = abi.decode(_data, (address, uint256));
        _handleTransfer(recipient, amount);
    }
    
    function _dispatchMessage(uint32 _destChainId, address _recipient, uint256 _amount) internal virtual {
        // This function now assumes fees have been collected.
        // The actual fee payment to VIA's protocol happens here.
        // This might involve passing msg.value or calling a specific payable function.
        // CONSULT VIA DOCS for how _sendMessage handles fee payment.
        _sendMessage(_destChainId, abi.encode(_recipient, _amount));
    }

    function _handleTransfer(address _recipient, uint256 _amount) internal virtual;

    // --- NEW: Internal Fee Collection Logic ---
    function _collectFees(address _from, uint32 _destChainId) internal {
        uint256 sourceFee = sourceFees[_destChainId];
        uint256 destGas = destinationGasFees[_destChainId];

        // Check against max fee limits for protection
        require(sourceFee <= maxFeeLimits[_destChainId], "Fee exceeds max limit");
        require(destGas <= maxGasLimits[_destChainId], "Gas exceeds max limit");
        
        if (sourceFee > 0) {
            feeToken.safeTransferFrom(_from, address(this), sourceFee);
        }
        if (destGas > 0) {
            wrappedGasToken.safeTransferFrom(_from, address(this), destGas);
        }
    }

    // --- NEW: Access-Controlled Fee Management Functions ---
    function setFeeTokens(address _feeToken, address _wrappedGasToken) external onlyOwner {
        feeToken = IERC20(_feeToken);
        wrappedGasToken = IERC20(_wrappedGasToken);
    }

    function setFees(uint32 _chainId, uint256 _sourceFee, uint256 _destinationGas) external onlyOwner {
        sourceFees[_chainId] = _sourceFee;
        destinationGasFees[_chainId] = _destinationGas;
    }

    function setMaxFeeLimits(uint32 _chainId, uint256 _maxFee, uint256 _maxGas) external onlyOwner {
        maxFeeLimits[_chainId] = _maxFee;
        maxGasLimits[_chainId] = _maxGas;
    }

    // --- NEW: Emergency Recovery Functions ---
    function recoverToken(address _tokenAddress, uint256 _amount) external onlyOwner {
        IERC20(_tokenAddress).transfer(owner(), _amount);
    }

    function recoverNative(uint256 _amount) external onlyOwner {
        payable(owner()).transfer(_amount);
    }
}
Step 2: Updating the ViaERC20.sol (Burn-and-Mint) Contract
The bridge function is updated to call the new _collectFees function. The initialize function is also updated to set the owner.

Solidity

// SPDX-License-Identifier: MIT
pragma solidity =0.8.17;

import "../routers/ViaTokenRouter.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20BurnableUpgradeable.sol";

contract ViaERC20 is ERC20Upgradeable, ERC20BurnableUpgradeable, ViaTokenRouter {
    
    function initialize(
        string memory _name,
        string memory _symbol,
        uint256 _initialSupply,
        address _initialOwner // Add owner for fee management
    ) public initializer {
        __ERC20_init(_name, _symbol);
        __ERC20Burnable_init();
        __Ownable_init(); // Initialize OpenZeppelin's Ownable
        transferOwnership(_initialOwner); // Set the owner

        if (_initialSupply > 0) {
            _mint(msg.sender, _initialSupply);
        }
    }

    function bridge(uint32 _destChainId, address _recipient, uint256 _amount) external {
        // --> ADDED: Collect fees before proceeding <--
        _collectFees(msg.sender, _destChainId);

        _burn(msg.sender, _amount);
        _dispatchMessage(_destChainId, _recipient, _amount);
    }

    function _handleTransfer(address _recipient, uint256 _amount) internal override {
        _mint(_recipient, _amount);
    }
}

Step 4: Deployment and Configuration Workflow 🚀
With the new contracts, your workflow becomes:

Deploy: Deploy your ViaERC20 or ViaERC20Collateral contracts to each chain, passing the initial owner's address in the constructor/initializer.

Set Fee Tokens: As the owner, call setFeeTokens() on each deployed contract to define which tokens will be used for fees (e.g., USDC and WETH addresses).

Set Fee Limits: Call setMaxFeeLimits() for each supported destination chain to establish a safety ceiling for costs.

Set Active Fees: Call setFees() for each destination chain to set the actual fees that users will pay per transaction.

User Interaction: Users must now approve your contract to spend not only the token they are bridging but also the feeToken and wrappedGasToken before calling the bridge function. Your dApp front-end needs to handle these multiple approvals.
